# Brewer's book — design

## Intent
Recipes in Create Brewery are hidden and found by experimenting. The brewer's book is the player's own diary of
those experiments: it remembers the best result the player ever got for each drink, at every stage. It is
**exclusive**: anyone may pick up or steal the book, but only its owner can read it.

## Goals
- New item **Brewer's book** (`brewery:brewer_book`, stack size 1). Craft: shapeless, book + glass bottle + wheat
  (builder's call on exact recipe is fine if this conflicts with something).
- **Binding:** the first real player (not a FakePlayer) who uses the book binds it. Component
  `brewery:book_owner` `{uuid, name}`. Tooltip: "Brewer's book of Kostya" / «Книга пивовара Kostya».
- **Journal lives on the server, not in the item.** World-level `SavedData` (`brewery_journal`, overworld data storage)
  keyed by player UUID. Losing the book loses nothing; a new book shows the same journal. Automation updates the
  journal while the owner is offline.
- **What gets recorded (approach A, picked by the user): your best result per drink, per stage.**
  - Kettle: when a brew finishes in a kettle with an owner and the winning recipe is a real drink (not the muddy
    brew), record for that drink: the mix (ingredient item ids with counts), the heat source level, and the stars.
  - Distillery: when a distillate is made (not spoiled) from wort whose `BrewerMark` names an owner UUID, record
    under the base drink: shaft RPM and stars.
  - Barrel: when aging finishes for a batch whose mark names an owner UUID, record under the base drink: barrel
    wood, days aged, and stars.
  - A stage's entry is replaced only when the new stars are strictly higher (ties keep the older record).
  - Only the kettle owner is credited (via the mark). Drinking or receiving drinks records nothing.
- **BrewerMark gains the owner's UUID** as an optional field `owner` (old marks without it still load and show the
  name, but credit nobody). The kettle stamps it.
- **Reading:** using the book opens a custom screen in the mod's style: a parchment two-page spread.
  - First spread: owner name and "Discovered N of M".
  - Then one spread per drink, in a stable order (recipe id order). Discovered drinks: name, best stars per stage,
    ingredient icons with counts, heat source, still RPM, barrel wood and days. Stages never reached show "—".
    Undiscovered drinks show "???".
  - Arrows (and mouse wheel / arrow keys) turn spreads.
- **Exclusivity is enforced on the server.** When a non-owner uses the book, the server sends no journal data at all;
  the client shows the same spread layout filled with scribbles rendered in Minecraft's `minecraft:alt`
  (enchanting-table) font plus a line "The handwriting is illegible…" / «Почерк неразборчив…». A modified client
  therefore cannot read stolen recipes.
- Art (book item texture, GUI texture) generated by `tools/gen_art.py`; EN + RU lang.

## Non-goals
- Showing the ideal recipe. The book shows only what the player actually achieved.
- Sharing, copying or teaching recipes to other players.
- Recording drinks the player tasted or got from others.
- JEI integration.

## Anti-goals
- A stranger learning anything about the owner's recipes from the book (names of discovered drinks included).
- Losing the journal when the book is lost, burnt or stolen.

## Constraints
- NeoForge 1.21.1, Create 6.0.10, Java 21. The mod has no network payloads yet: this adds the first
  (`RegisterPayloadHandlersEvent`, server → client "open book" payload).
- Unit tests via `gradlew build`, game tests via `gradlew runGameTestServer`; all must pass.
- Art only through `tools/gen_art.py`. Lang edits via Python json (`ensure_ascii=False, indent=2`).

## Approaches considered
- **Recording:** A (picked) — best actual result per stage; B — reveal the ideal recipe on first match (rejected:
  makes discovery trivial).
- **Look:** A (picked) — custom mod-style spread with item icons and stars; B — vanilla written-book screen with
  plain text (cheaper, but poor and unlike the rest of the mod's GUI).
- **Exclusivity:** server sends nothing to strangers (picked) vs. hiding it client-side (a modified client could read it).

## Settled after the builder check (designer's calls)
- **Who is credited when inputs mix:** the distillery already keeps the first wort's mark ("first mark wins") and the
  barrel keeps one mark per batch slot; credit goes to that mark's owner. A mark without `owner` credits nobody.
- **Finding the base drink:** `DrinkData.stage` already names the stage; `BrewingRecipe.profileOf` /
  `profileDistilledTo` map it back to the drink profile, so the mark needs no drink id.
- **Stages a drink does not have** (e.g. beer is never distilled) are left out of its page, not shown as "—";
  "—" means a stage the drink has but the player has not reached yet.
- **Stranger's view:** the payload carries only "unreadable" — no count, no ids. The client shows a fixed three
  spreads of scribbles. "Discovered N of M" appears only to the owner.
- **Owner's payload:** drink ids, the total number of drinks, and the entries (item ids + counts, heat level, RPM,
  wood id, days, stars). Names come from the existing lang keys `drink.brewery.<id>` and item registry on the client.
- **Owner name** shown on the book is the name captured at binding.

## Left to the builder
- Exact payload shape, screen layout pixels, page count when there are many drinks.
- Exact ingredient-count representation (the kettle's contents list).
- Where the journal-update hooks sit in the kettle, distillery and barrel code.
- Tests: unit tests for the "replace only when strictly better" rule and journal (de)serialization; game tests:
  owner's kettle records a drink; muddy brew and owner-less kettles record nothing; distillery and barrel credit
  the mark's owner; a book binds to its first user; a stranger's open payload carries no journal data.
